# Разработка продукта

Используй этот навык только по явному запросу пользователя для выбранной задачи. Вызов действует на дальнейшие шаги этой задачи в текущем чате; повторять его на каждом шаге не нужно. Для другой задачи и для продолжения в новом самостоятельном чате требуется явный вызов. При передаче блока отдельному автору передай также исходный вызов пользователя и границы задачи.

Навык определяет действия ИИ, результат каждого шага и передачу между авторами. Перед началом работы прочитай [обязательные правила](references/rules.md): они входят в состав навыка и действуют для выбранной задачи.

Сначала восстанови текущее состояние задачи, затем выполни ближайший разрешённый шаг. Подготовка решения не означает его принятия пользователем.

## Начало и продолжение

Прочитай обязательные правила среды и проекта. Изучи существующее поведение по коду, документации, карте модулей и относящимся к задаче Markdown-файлам. Запиши расхождения между описанием и кодом. При противоречии общих и проектных правил вынеси конкретный конфликт пользователю до реализации.

Найди документы задачи и решения пользователя. Если задача уже начата, прочитай [состояние и передачу работы](references/handoffs.md) и восстанови последнюю подтверждённую точку. Сохрани действующие согласования; не повторяй их без изменения версии. Если подтверждения нет, обозначь пробел.

Вопросы задавай после изучения доступных фактов. Не подменяй неизвестное требование своим предпочтением. Объясняй пользователю поведение продукта и выборы простыми словами, позволяя проверить результат без чтения кода.

## Перед переходом

Проверь, что разрешение относится к текущим версиям документов и блоку. Запиши факт и источник решения в состоянии задачи. Молчание, успешный тест или согласие с прежней версией не разрешают новый вариант. Когда меняется одно решение, объясни, какие зависимые согласования устарели; сохрани остальные.

Для кода используй TDD по умолчанию. Если характер конкретной задачи или блока требует иного подхода, представь причину, другой порядок разработки и проверки и границы исключения. Дождись решения пользователя; остальные контрольные точки сохраняются. Для визуального результата отдельно согласуй способ проверки: например, сравнение экрана в заданном размере, сценарий взаимодействия и доступность. Не выдавай автоматические тесты за приёмку внешнего вида.

Автор тестов не получает новую реализацию, автор реализации не меняет принятые тесты, ревьюер не исправляет файлы сам. Обеспечь отдельные сессии и разрешённые им состояния файлов по [порядку передачи](references/handoffs.md). Если помощников нет, подготовь пакеты для отдельных чатов и сообщи пользователю ближайшее действие. Не заменяй независимость сменой роли в текущем чате.

Храни материалы задачи в самом проекте. Используй существующие места и команды; не навязывай новый каталог или систему документов. Небольшая задача может иметь один короткий документ со всеми разделами, но сохраняет согласования, независимость и доказательства проверок.

Создай или обнови одну задачу в Linear на проверяемый результат по [составу задачи в Linear](references/acceptance.md). При отсутствии доступа к Linear сохрани её описание локально, сообщи об этом и продолжай разрешённую работу. Навык не требует конкретного редактора, Runner, коннектора или встроенных помощников.
