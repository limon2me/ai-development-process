# Общий процесс разработки с ИИ

Пакет задаёт согласованный порядок работы для любых проектов: изучение → ТЗ → архитектура и блоки → тесты → реализация → независимое ревью → приёмка блока → приёмка задачи в использовании.

Общие правила и навык хранятся в этом отдельном Git-репозитории. Первое подключение на каждом компьютере и в каждой среде пользователь выполняет самостоятельно. Подключение не изменяет проекты.

Навык оформлен по [Agent Skills](https://agentskills.io/specification). Его папка содержит всё необходимое для процесса; ссылки навыка ведут только к файлам внутри неё. Особые инструменты, язык программирования, Runner и Linear не являются условием работы. Без встроенных помощников используются отдельные чаты; без Linear локально сохраняется описание задачи, подготовленное для Linear.

## Получить пакет на двух компьютерах

Репозиторий можно разместить в любой папке. В командах ниже `PROCESS_REPO` — путь к вашей копии; при другом расположении замените его. Общие правила и навык не содержат путей к конкретному компьютеру.

```sh
PROCESS_REPO="$HOME/Projects/ai-development-process"
```

На втором компьютере используйте копию той же версии: clone своего удалённого Git-репозитория или перенос всей папки. Удалённый адрес здесь не задан. Для синхронизации через Git сначала нужны ваш commit и выбранный вами remote; создание пакета само по себе не публикует его.

При наличии remote клонирование выглядит так; вместо строки в кавычках укажите реальный адрес:

```sh
git clone 'АДРЕС_ВАШЕГО_РЕПОЗИТОРИЯ' "$PROCESS_REPO"
```

Перенос копии между компьютерами не заменяет подключение в каждой среде. Ссылки на папки навыка создаются заново на каждом компьютере.

## Codex: общие правила

Откройте глобальный `~/.codex/AGENTS.md` и добавьте в него полный текст [RULES.md](RULES.md), сохранив остальные свои инструкции. Если задан другой `CODEX_HOME`, используйте его каталог. Если уже есть непустой `AGENTS.override.md`, Codex читает его вместо глобального `AGENTS.md`: поместите блок процесса в реально используемый файл. Начните новую сессию после изменения. [Официальный порядок загрузки](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Не ограничивайтесь ссылкой на репозиторий: текст обязательных правил должен быть в глобальных инструкциях. Так согласования остаются видимыми до загрузки навыка.

## Codex и Cursor: один локальный навык

Обе среды документируют пользовательский каталог `~/.agents/skills`. На каждом компьютере можно подключить одну папку навыка для обеих сред. Codex поддерживает символические ссылки; для независимости от расположения проекта ссылка указывает на этот репозиторий. [Codex](https://learn.chatgpt.com/docs/build-skills), [Cursor](https://prod.cursor.com/docs/skills).

Сначала проверьте, нет ли уже `product-development` в каталогах установленных навыков. Сохраните существующую версию и выясните её происхождение; не создавайте несколько копий с одинаковым именем. При свободном пути:

```sh
mkdir -p "$HOME/.agents/skills"
ln -s "$PROCESS_REPO/skills/product-development" "$HOME/.agents/skills/product-development"
```

Если предпочитаете копирование, перенесите **всю** папку `skills/product-development`, включая `references`, в `~/.agents/skills/product-development`. После обновления репозитория эту копию нужно обновлять отдельно. Для обнаружения навыка начните новую сессию; при необходимости перезапустите приложение. Название в списке — `product-development`.

Эти пути относятся к локальному компьютеру. При работе в удалённой среде проверяется её собственное подключение; локальная установка не доказывает его наличие там. [Ограничения переноса навыков Cursor](https://prod.cursor.com/docs/skills).

## Cursor: общие правила

В настройках **Customize → Rules → User Rules** добавьте полный текст [RULES.md](RULES.md), сохранив остальные инструкции. Этот механизм применяется ко всем проектам в Agent (Chat). Он не применяется к Tab и Inline Edit; проверку процесса выполняйте в Agent. [Официальная документация](https://prod.cursor.com/docs/rules).

Начните новый чат и выполните [проверку подключения](validation/connection-check.md).

## Claude Desktop

В **Settings → Instructions for Claude** добавьте полный текст [RULES.md](RULES.md), сохранив остальные инструкции. Это настройка аккаунта для разговоров с Claude; проверяйте её в аккаунте, используемом на каждом компьютере. [Официальная документация](https://support.claude.com/en/articles/10185728-understanding-claude-s-personalization-features).

Для навыка включите **Code execution and file creation**, если функция доступна в аккаунте. В **Customize → Skills → + → Create skill → Upload a skill** загрузите ZIP с папкой `product-development` и включите навык. В организациях доступ также зависит от настроек владельца. [Порядок загрузки и условия](https://support.claude.com/en/articles/12512180-use-skills-in-claude).

Архив должен содержать `product-development/SKILL.md` и всю папку `product-development/references`. Можно использовать подготовленный `dist/product-development.zip` или собрать его из текущей версии:

```sh
mkdir -p "$PROCESS_REPO/dist"
cd "$PROCESS_REPO/skills"
zip -r "$PROCESS_REPO/dist/product-development.zip" product-development -x '*/.DS_Store'
```

`dist` — производные файлы, они не входят в Git. Если уже существующий ZIP собран из прежней версии, удалите только этот производный архив перед новой сборкой, чтобы в нём не остались удалённые файлы. Загрузка в Claude — отдельная копия: изменение Git-репозитория её не обновляет. В новом чате выполните проверку подключения.

## Среда без поддержки навыков

Добавьте текст `RULES.md` в её глобальные пользовательские инструкции. Передайте `SKILL.md` обычным документом или текстом, а относящиеся к текущему шагу файлы из `references` приложите по запросу ИИ. Все документы шагов можно приложить сразу, если среда не умеет открывать связанные файлы. Содержание и согласования остаются теми же.

Стартовая фраза для такой среды:

```text
Применяй приложенные RULES.md и product-development/SKILL.md
как мой процесс разработки. Описания шагов находятся в приложенных
references. Начни с исследования моего проекта и ближайшего
несогласованного шага; уже подтверждённые решения сохрани.
```

Если среда не имеет доступа к проекту, приложите требуемые проектные материалы и сообщите об этом ограничении. При отсутствии самостоятельных команд проверки ИИ готовит инструкции, пользователь запускает их и возвращает фактические результаты. ИИ не утверждает, что исследовал недоступные файлы или выполнил команды.

Если среда вообще не поддерживает глобальные инструкции, передавайте правила в начале каждого рабочего чата. Это ручное подключение; обязательность во всех новых чатах автоматически не обеспечена.

## Правила проекта и отдельные авторы

Существующие проектные инструкции остаются в проектах. Общий пакет задаёт порядок согласований, а проект — свои ограничения и проверки. При конфликте ИИ должен показать конкретное противоречие до реализации. У сред есть собственный приоритет инструкций, поэтому проверка фактического поведения обязательна; один глобальный файл не является техническим блокировщиком команд.

Один навык ведёт все шаги. Автор тестов, автор реализации и ревьюер — три разные сессии с ограниченными материалами по [порядку передачи](skills/product-development/references/handoffs.md). Без помощников пользователь открывает отдельные чаты. Смена названия роли в одном чате не обеспечивает независимость. Исходное состояние проекта для автора тестов сохраняется отдельно от новой реализации.

## Обновление

Обновляется содержимое этого репозитория: общие правила, навык и инструкции. Изменения процесса пользователь принимает и переносит в свои подключения сам. Это не обновление кода проектов или Runner.

1. Получите выбранную версию репозитория на обоих компьютерах. При настроенном remote и отсутствии локальных изменений можно выполнить `git -C "$PROCESS_REPO" pull --ff-only`.
2. Сравните `RULES.md` с блоком процесса в глобальных инструкциях каждой среды и перенесите изменения, сохранив прочие инструкции.
3. Символическая ссылка использует обновлённые файлы репозитория; установленную копию папки обновите отдельно. В Claude заново соберите ZIP, замените установленный навык и проверьте его включение.
4. Начните новые сессии и повторите [проверку подключения](validation/connection-check.md). Отметьте фактически проверенные компьютер, среду и версию.

Для проверки одинакового содержимого на двух компьютерах сравните commit (`git -C "$PROCESS_REPO" rev-parse HEAD`). Если commit ещё нет или есть локальные изменения, сравните контрольные суммы исходных файлов:

```sh
cd "$PROCESS_REPO"
shasum -a 256 RULES.md skills/product-development/SKILL.md skills/product-development/references/*.md
```

Совпадение версии подтверждает одинаковый пакет; поведение нового чата проверяется отдельно.

Подготовленная версия правил и навыка также зафиксирована в [контрольных суммах](validation/process-files.sha256). Для проверки этой версии выполните из корня репозитория `shasum -a 256 -c validation/process-files.sha256`. Если вы меняете процесс, обновите суммы после его проверки; старые суммы относятся к прежнему содержимому.

## Проверка пакета и первый пример

Проверка структуры и ссылок дополняется [поведенческими сценариями](validation/scenarios.md). Для повторного прогона отдельной сессии передаются правила, навык и только входные данные сценария, без критериев и выводов предыдущего прогона. Наблюдаемый ответ сравнивается с критериями после завершения. Итоги сохраняются в [отчёте](validation/report.md).

До первого рабочего примера пользователь принимает [формат ТЗ](skills/product-development/references/specification.md). Затем пользователь описывает, что хочет сделать с Session Runner. Этот новый запрос проходит обычный процесс; требования к Runner заранее не определены. Проверка пакета и подключений не считается фактической приёмкой будущих изменений Runner.
